# JavaScript 事件循环（Event Loop）

## 一句话总结

JavaScript 主线程是单线程，Event Loop 在**调用栈清空后**，按「先清空所有微任务，再执行一个宏任务」的循环规则，把异步回调推回调用栈执行，从而实现非阻塞的异步。

---

## 背景

### 1. 为什么是单线程？

浏览器里 JS 的主要工作是**操作 DOM**。如果允许多个线程同时改 DOM，会出现竞态（一个线程删了节点，另一个线程还在改它），状态无法预测。所以 JS 从设计上就是**单线程**——同一时刻只做一件事。

### 2. 单线程带来什么问题？

如果所有代码都同步执行，遇到「网络请求 / 定时器 / 读取文件」这种耗时操作，主线程会被卡住，页面**冻结、无法响应点击**。这显然不可接受。

### 3. 怎么解决？—— 把耗时操作"外包"出去

JS 把耗时任务交给**宿主环境**（浏览器 / Node）的其他线程去处理（网络线程、定时器线程等），自己继续往下跑。等外包任务完成，再把"后续要做的回调"放回主线程执行。

**Event Loop 就是这个"回收调度的总指挥"。**

> 没有 Event Loop：主线程被阻塞 → 界面卡死。
> 有 Event Loop：耗时操作外包、完成后再排队回来 → 非阻塞。

---

## 核心概念

运行时由这些角色协作（以浏览器为例）：

```
┌────────────────────────────────────────────────────────┐
│                       JavaScript 运行时                   │
│                                                          │
│  ┌──────────────┐                                        │
│  │  调用栈       │  Call Stack —— 同步代码执行的地方（LIFO）│
│  │  (Stack)     │                                        │
│  └──────────────┘                                        │
│                                                          │
│  ┌──────────────┐                                        │
│  │  堆 (Heap)   │  对象、闭包等引用类型数据存放处          │
│  └──────────────┘                                        │
│                                                          │
│  ┌────────────────────────────────────────────┐         │
│  │  宿主环境（浏览器提供的 Web API，其他线程）  │         │
│  │  setTimeout / fetch / DOM 事件 / ...        │         │
│  └────────────────────────────────────────────┘         │
│            │ 完成时把"回调"丢进对应队列                    │
│            ▼                                             │
│  ┌─────────────────────┐  ┌─────────────────────────┐   │
│  │ 宏任务队列           │  │ 微任务队列              │   │
│  │ (Task Queue)        │  │ (Microtask Queue)       │   │
│  │ setTimeout/I/O/UI   │  │ Promise.then / queue-   │   │
│  │                     │  │ Microtask / MutationObs │   │
│  └─────────────────────┘  └─────────────────────────┘   │
│            ▲                        ▲                     │
│            └────────────────────────┘                     │
│                   Event Loop 调度                         │
└────────────────────────────────────────────────────────┘
```

### 谁是宏任务（Macrotask），谁是微任务（Microtask）

| 宏任务（Macrotask）                                     | 微任务（Microtask）                   |
| -------------------------------------------------- | -------------------------------- |
| 整体 script 代码                                       | `Promise.then / catch / finally` |
| `setTimeout` / `setInterval`                       | `queueMicrotask()`               |
| I/O（网络、文件）                                         | `MutationObserver`（浏览器）          |
| UI 交互事件（click 等）                                   | `process.nextTick`（Node，优先级最高）   |
| `setImmediate`（Node）                               |                                  |
| 渲染相关（如 `requestAnimationFrame`，在渲染阶段执行，不归入普通宏任务队列） |                                  |

## 底层原理

### Event Loop 每一轮的规则

```
每一轮循环：
1. 从宏任务队列取【一个】宏任务执行（最开始是整段 script）
2. 执行过程中若产生微任务，放入微任务队列
3. 【清空】微任务队列里的【所有】微任务（包括执行微任务时新产生的微任务）
4. 必要时进行渲染（浏览器）
5. 回到第 1 步，取下一个宏任务
```

**两个关键点：**

1. **微任务优先**：每执行完一个宏任务，会先把微任务队列"清空到底"，才轮到下一个宏任务。
2. **微任务会被"连坐"清空**：执行微任务时如果又产生新的微任务，新微任务也会在同一轮被立即执行（直到队列空）。

### 为什么 `setTimeout(fn, 0)` 不是"立即执行"？

- `0` 毫秒是"尽快"，浏览器实际最小延迟约 4ms。
- 更重要的是：即使延迟为 0，回调也只是**尽快入宏任务队列**，必须等**当前调用栈清空 + 所有微任务跑完**才轮到它。

```

        │            整段 script 作为第一个宏任务     │
        └────────────────────┬────────────────────┘
                             ▼
                    ┌─────────────────┐
                    │   调用栈执行同步  │
                    │   代码           │

                        │         │ 遇到 setTimeout/fetch/事件
                        │         ▼

                        │         └── 微任务 → Microtask Queue
                        ▼

                        │

        │  1. 清空【所有】微任务（循环到底）   │
        │  2. 取【一个】宏任务执行             │
        │  3. 回到 1                           │
        └───────────────────────────────────┘
```

## 经典例题

### 例题 1：最基础的顺序

```javascript
console.log('1')
setTimeout(() => console.log('2'), 0)
console.log('4')
Promise.resolve().then(() => console.log('3'))
```

**执行过程：**

1. 同步代码入栈：`console.log('1')` → 打印 `1`
2. `setTimeout(...)` → 交给 Web API，0ms 后回调入**宏任务队列**
3. `console.log('4')` → 打印 `4`
4. `Promise.resolve().then(...)` → 回调入**微任务队列**
5. 同步结束，栈空 → Event Loop 先**清空微任务** → 打印 `3`
6. 再取一个宏任务（setTimeout 回调）→ 打印 `2`

**输出：`1 4 3 2`**

> 注意 3 在 2 前面——因为微任务优先于宏任务。

### 例题 2：微任务"连坐"清空（易错）

```javascript
Promise.resolve().then(() => {
  console.log('微任务1')
  Promise.resolve().then(() => console.log('微任务1-1'))
})
Promise.resolve().then(() => console.log('微任务2'))
```

**执行过程：**

1. 微任务队列初始：`[p1, p2]`
2. 执行 p1：打印 `微任务1`，内部新 `.then` 把 `微任务1-1` 加入队尾 → 队列变 `[p2, p1-1]`
3. 取 p2：打印 `微任务2` → 队列变 `[p1-1]`
4. 取 p1-1：打印 `微任务1-1`

**输出：`微任务1` → `微任务2` → `微任务1-1`**

> 不是「微任务1 → 微任务1-1 → 微任务2」。新产生的微任务排在"当前批次已有微任务"之后。

## 实际开发中的应用

### 1. Vue 的 `nextTick`

Vue 更新 DOM 是**异步**的（批量、在微任务里做）。当你修改响应式数据后，DOM 不会立刻变。`nextTick(cb)` 内部用 `Promise.then`（微任务）把 `cb` 排到"DOM 更新之后"执行，所以回调里能拿到更新后的 DOM。

```javascript
count.value++
nextTick(() => {
  // 这里能读到更新后的 DOM
})
```

### 2. `fetch` / 网络请求

`fetch(...)` 本身是宏任务层面的 I/O，但它的 `.then / async` 后续处理是**微任务**，所以网络回来后"处理响应"会排在微任务阶段，早于其他 setTimeout。

### 3. 警惕微任务死循环

```javascript
function loop() {
  queueMicrotask(loop) // 永远产生新微任务
}
loop()
// 微任务永远清不完 → 宏任务（包括渲染）永远排不上 → 页面卡死
```

微任务里不断产生微任务，会饿死宏任务和渲染。这是和"同步死循环"不同的另一种卡死方式。

## 框架设计思想

**为什么 JS 选「单线程 + Event Loop」而不是多线程？**

- 多线程要处理锁、竞态、DOM 一致性，复杂度极高。
- 单线程 + 异步回调模型让"共享状态"问题天然消失（同一时刻只有一处代码跑）。
- 代价：一个**长同步任务**会阻塞渲染（如大循环）。所以有了 **Web Worker**——把重计算搬到另一个线程，通过消息通信，不阻塞主线程。

如果我是语言设计者，也会优先选"单线程主线程 + 宿主多线程外包"：开发简单，又能借宿主能力做非阻塞。

## 容易混淆的地方

| 混淆点                     | 正确理解                                                             |
| ----------------------- | ---------------------------------------------------------------- |
| `setTimeout(fn,0)` 立即执行 | 只是尽快入宏任务队列，要等栈空 + 微任务清空                                          |
| 微任务和宏任务同时排队，谁先          | **微任务永远先**（每轮清空所有微任务）                                            |
| 多个 `Promise.then` 顺序    | 按入队先后；微任务中产生的微任务排在当前批次之后                                         |
| 调用栈 vs 任务队列             | 栈是"正在执行"，队列是"等着执行"，Event Loop 把队列搬到栈 |
| 宏任务里包含渲染                | 宏任务之间浏览器可能渲染；微任务阶段不渲染                                            |
