# JavaScript 垃圾回收（Garbage Collection）

> 本章属于「内存管理」体系，建议分 2 次学：① 核心原理（可达性、标记清除、分代回收）→ ② V8 GC 性能优化（Stop The World、增量标记、并发回收）。本笔记是第一课。

## 一句话总结

JavaScript 的垃圾回收（GC）是**引擎自动完成的内存管理**：引擎从一组「根」出发，找出所有仍然被引用到的对象，其余对象占用的内存视为「垃圾」回收掉；V8 用「分代回收」策略让这个过程既高效又不明显卡顿。

---

## 背景：为什么需要垃圾回收

### 1. 内存的三个阶段

任何程序的内存都经历三个阶段：

```text
分配内存 (allocate)  →  使用内存 (use)  →  释放内存 (release)
```

- **基本类型**（number、string 等）：值直接存在栈上，函数执行完自动出栈，无需操心
- **对象**（引用类型）：存在堆上，可能被多个变量/作用域引用，生命周期不固定

### 2. 如果没有 GC 会怎样？

C/C++ 需要程序员手动 `malloc` / `free` 管理堆内存，历史上出过三类经典错误：

1. **忘记释放** → 内存越用越多，程序最终崩溃（内存泄漏）
2. **重复释放** → 直接崩溃（double free）
3. **释放后还在用** → 读到脏数据甚至崩溃（悬垂指针）

JavaScript 选择了把「释放」这一步**交给引擎自动完成**。代价是 GC 需要暂停代码执行去扫描对象（即 Stop The World），所以引擎的优化方向一直是：**让回收更快、让停顿更短**。

## 第一节：核心思维模型——可达性（Reachability）

GC 不关心对象"在不在被变量使用"，只关心一个问题：**从根出发还能不能找到它？**

### 根（Roots）

```text
根（Roots）
├── 全局对象（浏览器 window / Node globalThis）
├── 当前调用栈上的局部变量、参数
└── 各种全局注册表（模块缓存等）
        │
        │  通过引用链访问
        ▼
    可达对象 ── 保留，不动它
    不可达对象 ── 垃圾，回收
```

```text
    根 ──→ 对象A ──→ 对象B
     │
     └─→ 对象C         对象D（无人引用，垃圾）
```

只要从根出发走不通，哪怕它内部数据很"大很复杂"，也是垃圾。**这是理解一切内存泄漏的钥匙。**

---

## 第二节：标记-清除（Mark-and-Sweep）

最基础也最核心的算法，两步：

```text
Mark（标记）：从根出发，遍历所有引用链，把可达对象打上标记
Sweep（清除）：扫描整个堆，把没标记的对象内存回收
```

```text
  Mark 后:                 Sweep 后:
  ┌──────┬──────┐          ┌──────┬──────┐
  │ A ✓  │ B ✓  │          │ A ✓  │ B ✓  │
  ├──────┼──────┤          ├──────┼──────┤
  │ C ✗  │ D ✓  │   ──►    │ 空   │ D ✓  │
  └──────┴──────┘          └──────┴──────┘
   C 未被标记，清除        C 的内存被释放
```

---

## 第三节：为什么不用「引用计数」？

更早的方案是记录每个对象被引用的次数，归零就回收。它有个致命缺陷——**循环引用**：

```javascript
let a = {}
let b = {}
a.x = b
b.x = a
// a 和 b 互相引用，引用计数永远 ≥1，永不回收
// 但 a、b 其实已经没有任何「根」能到达它们了
```

所以现代引擎都用「从根出发的可达性」，引用计数只作为辅助。

---

## 第四节：分代回收（V8 的核心优化）

一个观察现象（Weak Generational Hypothesis）：**大多数对象朝生暮死，少数对象活得久**。于是 V8 把堆按对象年龄分成两代，用不同策略处理。

```text
                新生代 (Young Gen)              老生代 (Old Gen)
   存放          刚创建的对象                   存活久 / 晋升过来的对象
   容量          小（通常几十 MB 级）            大
   回收频率      高（空间小，很快装满）           低
   算法          Scavenger（复制式）             Mark-Compact（标记整理）

  ┌──────────────┐
  │  From Space  │──复制存活对象──► ┌──────────────┐
  │  To Space    │◄─────────────────│              │
  └──────────────┘                  └──────┬───────┘
        │                                  │
        └── 对象被复制 2 次仍存活 ──────────► 晋升到老生代
```

### 为什么新生代用复制（Scavenger）？

新生代对象绝大多数会死，所以复制时只搬「还活着的」对象，成本与**存活对象数量**成正比，而不是与**总对象数**成正比——在"垃圾多于存活"的场景下非常划算。复制完 From/To 两块空间互换，旧空间直接作废，天然没有碎片。

### 为什么老生代用标记-整理（Mark-Compact）？

老生代里存活对象多，复制代价大；且长期增删会产生内存碎片。所以用「标记 → 清除 → 整理」：标记存活对象，然后把存活对象移动到一起、紧凑排列，消除碎片。

### 什么时候触发 GC？

- **新生代**：空间快满时 → Minor GC（小回收，很快）
- **老生代**：内存占用达到阈值时 → Major GC（大回收，较慢）
- 每次 Major GC 都会短暂暂停 JS 执行（Stop The World）

> 现代 V8 已用**增量标记 / 并发标记**把这些暂停拆散、挪到后台线程，避免卡顿。这是下一课的内容。

## 第五节：结合实际开发——常见内存泄漏场景

「垃圾」的定义是**不可达**，所以一切泄漏的本质都是：**你以为用完了，但它仍然从根可达**。

| 场景 | 为什么泄漏 |
|---|---|
| 意外全局变量 `a = 1` | 挂到了 `window` 上，永远可达 |
| `setInterval` / `setTimeout` 未清理 | 回调里持有的对象一直可达 |
| `addEventListener` 未 `removeEventListener` | 监听器被全局注册表保留 |
| 闭包被长生命周期变量持有 | 闭包锁定了整个外层作用域 |
| 已移除的 DOM 仍被变量引用 | `el.remove()` 后变量仍指向它 |
| 用 `Map`/`Set` 做缓存且 key 一直存在 | key 不释放，value 就永远可达 |

**Vue 业务中最常见的**：

```javascript
// 组件销毁前记得清理定时器和监听
beforeDestroy() {
  clearInterval(this.timer)
  window.removeEventListener('resize', this.onResize)
}
```

**排查工具**：Chrome DevTools → Memory → 拍两次 Heap Snapshot，对比 `Retained Size` 增长的对象；或用 Allocation Timeline 录制观察分配。

## 框架设计思想：如果我是 V8 作者

三个关键权衡：

1. **为什么选可达性而非引用计数** → 引用计数解决不了循环引用，且每次赋值都要更新计数（性能开销），可达性一次遍历全解决。
2. **为什么分代** → 用「对象年龄越大越可能存活」的经验规律，对不同年龄对象用不同算法，本质是**针对数据特征做策略分化**。这和 Vue 里 computed 缓存、diff 时优先复用同类型 VNode 是同一种思维。
3. **新生代复制 vs 老生代整理** → 复制式在"存活率低"时高效，整理式在"存活率高"时高效。没有银弹，只有匹配场景的权衡。

## 第六节：易错题精讲（练习 3 / 9 / 10）

> 三题同一条主线——**「谁还在引用它，决定了它生死」（可达性）**。

```text
根 (root)
│
├── globalThis / 模块顶层变量
│     └── leakHolder ──(闭包)──► big            ← 练习10：活着，gc 收不掉
│
├── 调用栈局部变量（函数执行期间）
│     └── a ──► b ──► a（整个环无根可达）       ← 练习3：死了，被回收
│
└── 事件循环的活跃句柄
      └── setInterval ──(回调)──► 引用的对象     ← 练习9：不清理就一直活着
```

### 练习 3：循环引用，为什么反而被回收？

**一句话**：GC 的判断单元不是"单个对象"，而是"从根出发能走到的整张可达性图"。

```text
① IIFE 执行中：   调用栈 → a → b → a（互指），此时 a、b 都在栈上，可达
② IIFE 结束：     调用栈帧弹出，局部变量 a、b 被销毁
③ 现在从根出发遍历：
   根 → 全局对象、调用栈……
   根本找不到任何路径能走到 a 或 b
④ 整个环（a、b 及其 ref 属性）整体不可达 → 全部标记为垃圾 → 一次性回收
```

对比**引用计数**为什么会卡死：

```text
引用计数：a.ref = b  → b 的计数 +1
          b.ref = a  → a 的计数 +1
          a、b 的计数永远 ≥ 1，永远不归零 → 泄漏
```

只要整个环没有外部引用指向它，管它内部互相指多少次，都是垃圾。

> **观测提醒**：练习 3 用两个空对象，`heapUsed()` 的波动都比它们大，看不出回收。要真看到效果，把环里的对象做大：
>
> ```javascript
> ;(function () {
>   const a = { data: new Array(3_000_000).fill('x') }
>   const b = {}
>   a.ref = b
>   b.ref = a
>   console.log('  环创建后:', mb(heapUsed()))
> })()
> gc()
> console.log('after gc:', mb(heapUsed())) // 会明显下降
> ```

### 练习 9：setInterval 为什么不清理，进程就不退出？

**一句话**：Node 进程"什么时候退出"，取决于事件循环里还有没有**活跃句柄（active handle）**。

Node 不是跑完代码就退出的，它有一个**事件循环**在持续"问"：还有没有事要做？判断标准有两类：

```text
① 任务队列里还有任务（回调、IO 回调等）
② 还有活跃句柄（timer、server、socket 等"挂着的资源"）
两者都空 → 进程退出
```

`setInterval` 干了两件事：

```text
setInterval(cb, 1000)
   │
   ├── ① 在 libuv 的 timers 里注册一个 timer 句柄  ← 这是活跃句柄，让事件循环"不空"
   └── ② 把 cb 和它引用的作用域挂到 timer 上       ← 引用从这里开始
```

只要 timer 句柄存在，事件循环就觉得"还有活要干"，进程就一直挂着。`clearInterval` 把句柄移除，事件循环空了，进程自然退出。

**串起来看**（练习 9 和泄漏的关联）：

```text
timer 句柄存活
   → 回调函数存活
   → 回调闭包捕获的作用域存活
   → 作用域里的任何大对象存活
```

Vue 里最常见的泄漏就是这条链：

```javascript
// 组件里
mounted() {
  this.timer = setInterval(() => {
    this.count++          // 回调引用 this（整个组件实例）
  }, 1000)
}
// beforeDestroy 不写 clearInterval(this.timer)
// → 组件实例被回调引用着，永远从根可达，切换路由也回收不掉
```

### 练习 10：闭包捕获了大对象，为什么 gc 后还在？

**一句话**：闭包"捕获"的不是某个变量，而是**整个变量环境（closure）**；只要闭包从根可达，被捕获的一切都跟着活。

```text
根（模块顶层）
   └── leakHolder（全局可达）
         └── 闭包函数（被全局变量持有）
               └── 变量环境中的 big（被闭包捕获）
                     └── 3_000_000 长度的数组
```

`leakHolder` 是全局变量，从根出发**一步就能到达闭包**，闭包又持有着 big 的引用，所以 big 虽然"只活在一个函数里"，却因为闭包被全局持有而永远可达。

修复就是**断开链头**：

```javascript
leakHolder = null   // 根到闭包的引用断了
gc()                // 闭包不可达 → 它的变量环境不可达 → big 一起被回收
```

### 统一检查清单

判断一段代码会不会泄漏，只问一句话：**谁还拿着它？从根出发，有几条路能到它？**

- 没人拿、路断 → 垃圾，会被回收（练习 3）
- 被事件循环的定时器/监听器拿着，且从不清理 → 活到进程结束（练习 9）
- 被全局变量/全局闭包拿着 → 活到页面关闭（练习 2、10）

对应的三个修复动作：`clearInterval` / `removeEventListener`（断开事件循环的引用）、`obj = null`（断开根到对象的引用）、用 `WeakMap`/`WeakSet`（不阻止回收地存引用）。

## 总结

**核心知识**：内存三阶段 → 栈/堆 → 可达性 → 标记清除 → 分代回收（新生代复制 + 老生代整理）。

**容易混淆**：

- GC 回收的是「不可达」的对象，不是「不用的」对象
- 闭包本身不会泄漏，**被长期持有的闭包**才会泄漏
- 引用计数是历史方案，现代引擎用的是可达性

**实际应用**：写业务时下意识检查定时器、监听器、全局变量、缓存容器；用 DevTools Memory 面板排查线上内存问题。

---

## 本节重点

1. 内存生命周期：分配 → 使用 → 释放
2. 可达性：从根出发能找到 = 可达（保留），找不到 = 垃圾（回收）
3. 标记-清除：Mark + Sweep 两步
4. 引用计数的缺陷：循环引用无法回收
5. 分代回收：新生代复制式（Scavenger）+ 老生代标记整理（Mark-Compact）
6. 晋升机制：对象被复制 2 次仍存活 → 升入老生代
7. 内存泄漏本质 = 对象仍然从根可达
