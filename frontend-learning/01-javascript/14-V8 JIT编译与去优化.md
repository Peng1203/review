# V8 JIT 编译与去优化

## 前置知识 & 知识网络

- **依赖**：V8 编译流水线（Parser → AST → Ignition → TurboFan）、隐藏类与内联缓存
- **影响**：把 V8 运行时板块收口 → 之后可无缝进入浏览器渲染、Vue 原理中"为何要稳定类型/形状"的实践认知

---

## 一句话总结

TurboFan 不会等到函数被调用才编译，而是**先让 Ignition 跑起来收集运行时反馈（类型、隐藏类、IC 命中）**，再把这些反馈当成"证据"做**激进推测优化**；为了保证"推测错了还能对"，它在插入类型检查的同时，保留字节码版本和**去优化点**——一旦运行时检查失败，就**反优化（deopt）回退到解释执行**，并在反馈里"记仇"，避免反复优化。

---

## 背景：为什么需要 JIT 而不是"直接编译一次"？

### 1. 传统"解释 vs 编译"的二分法不够用了

静态语言（C++）编译一次就得到机器码，运行时不再需要"思考"。

JS 是动态类型语言，**编译时不知道变量的类型**。如果按静态语言思路：等到变量类型确定后再编译 → 太晚；如果每次赋值都做类型分发 → 太慢。

JIT（Just-In-Time，即时编译）的答案是**动态分阶段**：

```text
阶段一：解释执行（Ignition）——先跑起来，顺便收集运行时信息
阶段二：当信息足够时——TurboFan 编译出针对"真实类型"的优化机器码
阶段三：运行时发现假设被打破——回退（去优化）到字节码继续跑
```

### 2. 为什么不能"把所有函数都编译成优化机器码"？

- 优化编译本身耗时、占内存
- 大部分函数只跑几次，为它们做全量优化是浪费
- JIT 用"热点探测"把资源集中在"真正频繁执行"的代码上

```text
不优化：每次解释执行，简单但慢
全优化：启动巨慢、内存爆炸（V8 早期全量 JIT 的教训）
JIT：只优化热点 → 启动快 + 热点快 ← V8 的现代路线
```

## 第一节：TurboFan 的类型推测与优化手段

### 1. 类型推测：拿运行时反馈"当证据"

TurboFan 编译某个函数时，会读取**该调用点的反馈向量（Feedback Vector）**——Ignition 在解释执行时记录下来的：

```text
function add(a, b) { return a + b }

add(1, 2)      // 反馈：a=Number, b=Number
add(3, 4)      // 反馈：a=Number, b=Number（稳定）
```

TurboFan 看到"一直 Number"，就推测 `a + b` 是整数加法，生成没有类型检查的机器码。

### 2. 优化手段一：类型专业化（Type Specialization）

```text
// 未优化（解释器通用逻辑）
Add 之前：先判断 a、b 是什么类型，再选加法策略

// TurboFan 优化后
直接执行整数加法指令（int 寄存器）
因为类型检查已在"进入函数时"一次性做完
```

这本质上就是把"动态分派"变成"静态假设"。

### 3. 优化手段二：内联（Inlining）

调用函数本身有开销（建立栈帧、跳转）。TurboFan 会把**热点函数的函数体"拷贝"到调用者内部**：

```text
// 优化前：每次都要 call add
function add(a, b) { return a + b }
for (...) { result += add(x, y) }

// TurboFan 内联后（概念上）
for (...) {
  // add 的代码被直接展开在这里，省掉 call/return
  result += x + y   // 且这里的 x、y 类型已知
}
```

**内联是 JIT 最大的性能来源之一**：不仅省掉调用开销，更重要的是——内联后，TurboFan 能**看到更长的代码片段**，做跨函数边界的优化（常量传播、消除冗余计算等）。

### 4. 优化手段三：OSR（On-Stack Replacement）

有些热点是**长循环**（循环体里跑几百万次，但函数本身只调用一次）：

```text
function longLoop() {
  for (let i = 0; i < 10000000; i++) {
    // 热点在"循环体内"，而不是"函数调用点"
  }
}
```

函数调用点的计数上不去 → 普通的"调用次数达标才优化"失效。V8 用 **OSR**：当**循环迭代次数**达到阈值时，在**循环体内部**把正在解释执行的栈帧"原地切换"成优化后的机器码，不用等函数返回再优化。

```text
解释器执行循环
   │  迭代 N 次后
   ▼
OSR：从解释器栈帧，直接切换到 TurboFan 优化的循环代码（同一循环继续跑）
```

## 第二节：类型检查与"检查后假设"

TurboFan 不是盲目相信反馈，它会在优化代码入口插入**类型检查**（Guard）：

```text
function add(a, b) {
  // TurboFan 生成代码：
  //   guard: a 是 Number？ 不是 → bailout（去优化）
  //   guard: b 是 Number？ 不是 → bailout
  return a + b   // 这里就可以放心做纯整数加法
}
```

这叫**推测优化（Speculative Optimization）**：Guard 失败 → 优化假设不成立 → 触发去优化。

## 第三节：去优化（Deoptimization）的完整流程

### 为什么必须能"回退"？

因为**动态语言无法保证未来**。TurboFan 做的所有优化都建立在"当前反馈"上，一旦未来出现了反馈里没见过的类型/形状，优化代码的结果就可能错。唯一安全方案：**放弃优化代码，回到字节码重新解释执行**。

### 触发条件（何时会去优化）

```text
① 类型假设被打破：说好的 Number，来了个 String
② 隐藏类变了：优化的对象形状，运行时变成了别的形状
③ 函数被 delete / 原型链变化（破坏内联假设）
④ 栈溢出 / 超出优化代码能处理的情况
```

### 去优化流程

```text
优化机器码中，guard 检查失败
   │
   ▼
bailout（跳出优化帧）
   │  必须恢复到"解释执行对应位置"的状态
   ▼
把优化帧的寄存器/栈状态，还原成字节码解释器能理解的样子
   │  （V8 通过优化时保存的 deopt 信息/翻译表做到）
   ▼
回退到字节码，从出错的位置继续解释执行
```

> 去优化是**昂贵的**——不仅丢弃了优化代码，还要做状态翻译。所以 V8 对"反复去优化的函数"有惩罚：记录 deopt 次数，多次后**降低优化优先级**，甚至不再优化（避免"优化→反优化"循环空转）。

### 实践中的"性能悬崖"

```text
稳定单一类型 → 优化顺利，飞快
类型忽而 number 忽而 string → 反复优化+反优化 → 比一直不优化还慢
```

（这正是上一章练习里"类型漂移 13.4ms vs 类型稳定 3.7ms"的内在原因）

## 第四节：Ignition 与 TurboFan 的分工协作

```text
        ┌────────────────────────────────────────┐
        │            Ignition（解释器）            │
        │  ① 启动就执行字节码（快起步）             │
        │  ② 收集运行时反馈：类型/隐藏类/IC命中     │
        │  ③ 维护反馈向量（每个调用点一条记录）     │
        └────────────────┬───────────────────────┘
                         │ 成为热点
                         ▼
        ┌────────────────────────────────────────┐
        │            TurboFan（优化编译器）        │
        │  ① 读反馈向量，做类型推测                │
        │  ② 内联热点函数                         │
        │  ③ 生成带 guard 的优化机器码             │
        └────────────────┬───────────────────────┘
                         │ guard 失败
                         ▼
        ┌────────────────────────────────────────┐
        │         Deopt（去优化，回到 Ignition）   │
        │  状态还原 → 字节码解释执行 → 记 deopt   │
        └────────────────────────────────────────┘
```

## 结合实际开发

1. **保持类型/形状稳定**是让 JIT 顺利工作的前提——上一章隐藏类讲的就是"形状"，本章的 guard 就是"类型的检查"，二者共同决定优化代码能否长期存活。
2. **警惕多态导致的性能悬崖**：热函数里避免"忽 number 忽 string"的写法（例如不清洗就拼接数据）。
3. **为什么源码里不写 `typeof` 也能被优化？** 因为 guard 替你做了——理解这一点后，就能明白"JS 不用类型标注也能接近静态语言速度"。

> Vue 场景（呼应）：Vue 的 render 函数、computed 频繁执行，若其中依赖的属性形态稳定（data 提前定义好），V8 能顺畅优化；若 data 运行时被不断动态加属性，形状不稳定，性能就受损。这解释了"为什么 Vue 官方建议 data 里把字段提前声明"。

## 框架设计思想（如果我是 V8 架构师）

1. **为什么用"反馈驱动"而不是静态类型推断？** 因为 JS 没有类型标注，唯一可靠的信息来源是"运行时的真实行为"。反馈驱动 = 用历史预测未来。
2. **为什么保留字节码而不把优化代码直接替换源码？** 为了去优化的退路——这是动态语言与静态语言最大的不同：静态语言编译完就删源，动态语言必须留一条"低配路径"随时兜底。
3. **为什么对反复去优化的函数"记仇"？** 优化是有成本的，如果函数不断反水（类型不稳定），继续优化是亏本的。**降级 = 止损**，把优化预算让给真正稳定的热点。

## 总结

**核心知识**：反馈驱动 → 类型推测 → 内联/OSR → guard 类型检查 → deopt 回退 → 反复 deopt 降级。

**容易混淆**：

- 优化不是"一次性"的：运行时反馈可能让函数被反复优化/反优化
- OSR（循环内优化）≠ 普通 JIT（函数调用点优化）
- 去优化不是 bug，是设计好的安全回退机制
- "类型稳定"的核心收益是 guard 长期命中、优化代码长期存活

**实际应用**：保持类型/形状稳定 = 让优化代码活得久；理解 deopt，就理解了为何"忽 number 忽 string"会撞上性能悬崖。
