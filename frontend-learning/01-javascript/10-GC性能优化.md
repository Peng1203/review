# V8 GC 性能优化（Orinoco）

> 本章是「垃圾回收」体系第二课，建议在第一课（可达性、标记-清除、分代回收）之后学习。核心讲清楚一个问题：**引擎如何在不卡顿用户的前提下完成垃圾回收**。

## 一句话总结

GC 要保证正确性，就得"冻结"正在运行的程序来扫描对象，这一冻结就是**停顿（Stop The World）**——停顿越长页面越卡。现代 V8 用**分代 + 增量标记 + 并发回收（Orinoco）**把一次大停顿拆成无数小步、甚至挪到后台线程，把"不可预测的大卡顿"变成"几乎无感知的小抖动"。

---

## 背景：为什么这课对前端尤其重要

### 1. 正确性要求"暂停"

GC 在标记对象时，如果 JS 同时还在改引用（比如 `a.x = c`），就会出现"一边标一边变"的矛盾——可能把**还活着的对象**当成垃圾回收掉，程序直接崩溃。所以早期方案很朴素：**先让程序完全停下，标完再继续跑**。

```text
JS 执行 → [STOP] → 标记 → 清除 → 整理 → [START] → JS 执行
                    <------ 几十~几百 ms 停顿 ------>
```

### 2. 同一问题，前后端影响天差地别

| | Node 后端 | 浏览器前端 |
|---|---|---|
| 停顿 100ms 的代价 | 请求延迟多 100ms，可接受 | 主线程卡 100ms = 掉 6 帧 |
| 优化优先级 | 吞吐量 | **低延迟 / 流畅度** |

浏览器 60Hz 刷新，**每帧只有 16.6ms** 预算给"JS + 样式 + 布局 + 绘制"。一次 GC 长暂停直接吞掉好几帧预算，用户体感就是滑动卡顿、点击没反应。**这就是为什么 V8 把大量精力花在缩短 GC 停顿上**。

## 第一节：三色标记法——增量标记的数学基础

要把"标记"拆成小步、且停下来还能接着干，V8 引入三色标记。给每个对象涂一个颜色：

```text
白色 White  还没被访问（可能是垃圾）
灰色 Grey   正在访问（它引用的对象还没处理完）
黑色 Black  已访问完（引用的对象都处理过了）
```

过程就像广度优先搜索：

```text
初始          处理中            结束
○ ○ ○        ● 灰 ● ○          ● ● ●
(全白)   →   灰被处理,          黑色 = 存活
             引用变灰,自己变黑   (白) = 垃圾
```

```text
┌─────┐    ┌─────┐    ┌─────┐
│ 灰  │───►│ 黑  │    │ 白  │   ← 垃圾
└─────┘    └─┬───┘    └─────┘
              │ 处理其引用
              ▼
          新的灰对象
```

**关键性质**：黑色对象永远不会被再次访问（引用已处理完）。所以**标记过程可以任意暂停**——只要记住"现在还有哪些灰对象"，下次从灰色继续即可。这给了"增量"可能性。

## 第二节：增量标记 + 写屏障——把大停顿拆成小步

有了三色法，就可以让主线程"标记一会儿、跑一会儿 JS、再标记一会儿"：

```text
早期 Full GC:
主线程: [JS] [ 停顿: 标记+清除+整理 ] [JS]
──────────────────┬──────────────────────→
           几十~几百 ms 卡顿

增量标记:
主线程: [JS][标][JS][标][JS][清][整][JS]
              ↑    ↑    ↑
           每次小步 ~1-5ms
```

但拆步引入一个**新问题**：标记间隙 JS 还在跑，如果它把一个**白色对象**赋值给一个**黑色对象**（黑色已处理完，不会再来访问），那个白色对象就被"漏标"了 → 被当垃圾回收 → 崩溃。

```text
黑色对象 a（引用已处理完）
JS 执行: a.x = 白色对象 w     ← 危险！a 不会再被遍历
```

V8 的解法是**写屏障（Write Barrier）**：每次给对象写属性时，检查"目标是否是黑色对象"，如果是，就把新引用的对象强制变灰，确保它下次被处理。

```text
JS 执行: a.x = w
写屏障: 发现 a 是黑色 → 把 w 变灰 → 下次增量标记会处理 w
```

**代价**：每次赋值属性都多一次检查。这就是为什么"增量标记总耗时 > 全停顿一次性标记"——**用更长总时间，换更短的单次停顿**。这个取舍对前端值得。

---

## 第三节：并行 vs 并发（Orinoco 的演进）

V8 的 GC 项目代号 **Orinoco**（亚马逊的一条河），分三个层次解决停顿：

```text
并行 Parallel      主线程 + 多个辅助线程同时标记/清除
                   ├─ 仍需 Stop The World
                   └─ 但停顿时间 ≈ 原来 ÷ 线程数（如 4 线程 → ~1/4）

增量 Incremental   主线程把标记拆成小步，穿插在 JS 之间（三色 + 写屏障）
                   ├─ 每次只停 1~5ms
                   └─ 总耗时变长

并发 Concurrent    标记工作完全放到后台线程
                   ├─ 主线程几乎不停顿
                   └─ 后台标的同时 JS 在改 → 靠写屏障同步进度（实现最复杂）
```

**V8 最终是组合拳**：

```text
新生代 Minor GC： 并行 + 半空间复制（对象多、活得少，一次快速搞定）
老生代 Major GC： 增量标记 + 并发标记 + 并行清除/整理
```

## 第四节：对前端的实际影响——长任务与掉帧

Chrome Performance API 里，主线程单次执行超过 **50ms** 叫**长任务（Long Task）**，而用户可感知的交互延迟指标 **INP** 统计的就是这个。GC 大停顿是长任务的经典来源：

```text
一帧预算 16.6ms
主线程: [JS][   GC 停顿 80ms   ][JS]...
              └── 用户点击、滚动在这期间无响应 = 掉帧
```

---

## 结合实际开发

**如何观察 GC**：
- DevTools → Performance 录制 → 时间轴上的紫色/灰色长条就是 GC 事件
- Node 里 `node --trace-gc app.js` 看 Minor/Major GC 日志

**如何减少 GC 压力**（不是让引擎快，而是别制造太多垃圾）：

1. **热路径少建对象**：`requestAnimationFrame` 里反复 `new` 对象、拼接大数组，等于每秒制造海量"朝生暮死"对象
2. **长列表用虚拟滚动**：常驻 DOM/对象数量降一个数量级，老生代压力大减
3. **别忘清理**：定时器、监听、全局缓存（第一课内容）
4. **动画/游戏场景用对象池**：复用对象，而不是反复创建销毁
5. **先测量再优化**：绝大多数业务代码不需要碰这个，DevTools 显示 GC 频繁才动手

## 框架设计思想

1. **为什么宁可复杂（三色、写屏障）也要避免全停顿？** → 前端的核心体验是"流畅"，对停顿零容忍。这是"把正确性交给算法保证，把性能开销摊到日常执行"的设计哲学。
2. **增量 vs 并发的权衡** → 增量实现简单但标记总时长变长；并发几乎不停顿但跨线程的写屏障同步极难写对。V8 的选择是**按代、按阶段分别用最合适的**——和第一课说的"针对数据特征做策略分化"一脉相承。
3. **体验优先于吞吐量** → Node 服务端其实可以接受全停顿（换吞吐量），浏览器不行。同一个引擎，为两种场景做了不同取舍。

## 总结

**核心知识**：停顿的由来（正确性）→ 三色标记（增量基础）→ 增量标记 + 写屏障 → 并行/并发（Orinoco）→ 长任务与掉帧。

**容易混淆**：

- 增量标记不是"更快"，是"总时间更长但单次停顿更短"
- 并行（Parallel）和并发（Concurrent）不同：并行仍需停，并发不停
- 写屏障是**每次属性赋值**的隐藏开销，不是 GC 时才发生

**实际应用**：先测量（DevTools/`--trace-gc`）→ 再针对热路径减少对象创建 → 业务里优先保证"不泄漏"（第一课）。

---

## 本节重点

1. Stop The World 是正确性要求，但长停顿毁掉前端流畅度
2. 三色标记：白色=垃圾候选，灰色=待处理，黑色=已处理完，暂停只发生在灰色
3. 增量标记把标记拆成 1~5ms 小步，穿插在 JS 任务间
4. 写屏障：黑色对象被赋值时，把新引用的白对象强制变灰，防止漏标
5. 并行 = 多线程同时做但需停顿；并发 = 后台线程做，主线程不停
6. V8 组合：新生代并行复制 + 老生代增量/并发标记 + 并行清除整理
7. 长任务（>50ms）与 INP 指标：GC 停顿是来源之一

## 思考题

1. 写屏障把白色对象变灰，为什么不是直接变黑？（提示：变黑意味着"引用都处理完了"，但 w 自己的引用处理完了吗？）
2. 如果并发标记时后台线程在标，主线程同时在改引用，却没有写屏障，会发生什么？（提示：漏标 → 回收活对象 → 崩溃）
3. 为什么 Node 后端可以接受全停顿 GC，浏览器不行？（提示：一帧预算、交互延迟）
