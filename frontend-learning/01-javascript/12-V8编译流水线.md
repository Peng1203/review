# V8 编译流水线（Parser → AST → Ignition → TurboFan）

## 前置知识 & 知识网络

- **依赖**：执行上下文、调用栈、闭包、作用域链、垃圾回收
- **影响**：隐藏类/内联缓存（下一章）、JIT 优化与去优化（再下一章）、深拷贝 / Vue 等源码阅读能力

---

## 一句话总结

V8 把 JS 源码变成机器能跑的东西，走的是 **「解析 → 字节码 → 机器码」的分层流水线**：`Parser` 把源码变成 `AST`，`Ignition` 把 AST 翻译成平台无关的**字节码**（先跑起来），跑的过程中 V8 盯住**热点函数**，交给 `TurboFan` 编译成**高度优化的机器码**；一旦假设被打破就**反优化**退回字节码。

---

## 背景：JS 到底是解释执行还是编译执行？

先破除一个常见误解。在浏览器里点开页面到 JS 真正执行，JS 引擎不是"读一行、执行一行"，而是一条完整的**编译流水线**：

```text
源码 (source code)
   │
   ▼
① Parser（解析器）
   │      词法分析 + 语法分析
   ▼
② AST（抽象语法树）
   │
   ▼
③ Ignition（解释器）───────────► ④ 直接执行字节码（起步阶段）
   │
   ▼
⑤ TurboFan（优化编译器）────────► 热点函数编译为机器码，飞速执行
```

**为什么需要这样分层？** 因为引擎要在两个矛盾目标之间找平衡：

1. **启动快**：页面一打开，代码最好立刻能跑
2. **执行快**：跑得久的代码（循环、频繁调用的函数）要尽可能快

一次性把全部源码编译成高度优化机器码 → 启动太慢；永远逐行解释 → 运行太慢。V8 用**"先快速跑起来，再逐步加速"**的策略同时满足两者。

## 第一节：Parser——从字符流到 AST

Parser 分两步走：

```text
词法分析 (Tokenize/Scanner)
  "let a = 1 + 2"
   ──► [{let}, {a}, {=}, {1}, {+}, {2}]   // 把字符切成"词法单元 token"
        │
        ▼
语法分析 (Parse)
  token 流 ──► 根据语法规则组装成树状结构
        │
        ▼
      let           ← AST 节点
     / │ \
   a   =   +
        (BinaryExpression)
        / \
       1   2
```

### 惰性解析（Lazy Parsing）——面试常考点

绝大多数函数**定义了但可能从不调用**（各种工具函数、回调）。如果 Parser 把所有函数体都完整解析成 AST，启动就会很慢。

V8 的做法是**只做表面解析（Pre-parsing）**：

```text
function outer() {
  function neverCalled() {   // 先只"扫一眼"语法是否正确
    const a = heavyCalc()    // 不急着生成完整 AST
    return a + 1
  }
  return 1                   // 外层完整解析
}
```

- 外层 `outer`：**完整解析（Eager）**，因为马上就要执行
- 内层 `neverCalled`：**惰性解析（Lazy）**，只验证语法、跳过变量绑定细节
- 只有当 `neverCalled` 真正被调用时，才会**二次解析（Re-parse）**成完整 AST

> 代价：惰性解析省了启动时间；但函数若确实被调用，二次解析又浪费时间。V8 有启发式——外层函数很短时往往直接把内层一起解析。内部还会用 `preparse data` 缓存来避免重复工作。

## 第二节：AST——代码的结构化表示

AST 就是**把代码拆成一棵树**，每个节点是"这句话在语法上是什么"。

```javascript
// 源码
const add = (a, b) => a + b

// 简化 AST
Program
└── VariableDeclaration
    └── VariableDeclarator
        ├── Identifier: add
        └── ArrowFunctionExpression
            ├── params: [Identifier a, Identifier b]
            └── BinaryExpression (+)
                ├── Identifier a
                └── Identifier b
```

AST 不只 V8 用——Babel、ESLint、TypeScript、Vue 模板编译全都在用 AST 做转换。**学会读 AST，等于掌握了所有编译类工具的公共语言**。

---

## 第三节：Ignition——AST → 字节码

AST 还不能直接执行，V8 用解释器 **Ignition** 把 AST 编译成**字节码（Bytecode）**。

字节码是什么？**一种介于 AST 和机器码之间的中间表示**——比机器码更接近人类可读、平台无关，比 AST 更接近机器、执行更快。

```text
add(a, b) { return a + b }

AST:
    BinaryExpression (+)
      ├── a
      └── b

Ignition 字节码（概念示意）:
  Ldar a1        // 加载参数 a
  Add r0, [0]    // 加上参数 b
  Return
```

- 字节码是**平台无关**的（同一份字节码跑在 x86、ARM 上）
- V8 首次执行走的是 Ignition：把字节码**逐条解释执行**
- 相比直接跑 AST，字节码紧凑、利于生成机器码

> 为什么 V8 中间加一层字节码？历史教训：早期 V8（2010 年代）"全量 JIT"——源码直接编译成机器码，启动快但**内存占用爆炸**（手机上多开几个网页就几百 MB）。2016 年引入 Ignition 字节码后，用"稍慢一点的启动 + 内存大幅下降"换来了移动端可行性。**又是"分层 + 权衡"的设计思想。**

---

## 第四节：TurboFan——热点函数 → 优化机器码

解释执行字节码虽然能跑，但比机器码慢得多。V8 在执行过程中会**记录每个函数的执行次数**，发现某函数成为**热点（Hot）**时，交给优化编译器 **TurboFan**，编译成**高度优化的机器码**。

```text
函数 f 被反复调用
   │  执行计数 达到阈值
   ▼
TurboFan 优化编译（后台线程做，不阻塞主线程）
   │  基于"运行时收集到的真实类型信息"
   ▼
优化后的机器码 ──► 替换原函数，下次调用直接跑机器码
```

**TurboFan 敢优化的底气是"推测"**：它观察这个函数被调用时的实参类型。比如发现 `add` 总是收到 number：

```text
TurboFan 的推测：a、b 永远是 number
   → 直接生成整数加法机器码，省去类型检查
   → 快几十倍
```

---

## 第五节：反优化（Deoptimization）——推测错了怎么办？

推测有风险。如果 `add` 跑了一万次都是 number，V8 优化成了"纯整数加法"；结果第 10001 次传进来一个字符串：

```text
f("a", "b")   // 类型假设被打破！
   │
   ▼
TurboFan 生成的优化代码作废
   │
   ▼
Deoptimization（反优化）：回退到 Ignition 字节码，重新解释执行
   并从优化前的字节码位置继续
```

这就是常说的 **"去优化导致性能悬崖"**：

```text
稳定的单一类型  → 优化顺利，飞快
忽而 number 忽而 string（类型不稳定）→ 反复优化又反优化 → 反而更慢
```

> TurboFan 内部会"叹气"：如果函数多次反优化，会降低它的优化优先级，不再轻易优化。

## 整体流水线总览

```text
源码
 │
 ▼
Parser ──────► AST ──────► Ignition ──────► 字节码 ─────► 解释执行（启动）
  ▲                │                            │
  │                │                            │ 成为热点
  │                │                            ▼
  │                │                     TurboFan 优化编译
  │                │                            │
  │                └─────(二次解析)──────────────┤
  │                                             ▼
  │                                      优化机器码（高速执行）
  │                                             │
  └──────── 反优化 deopt，退回字节码 ◄───────────┘
```

## 结合实际开发

1. **为什么"代码写法影响性能"？** 引擎的优化依赖类型稳定。写业务代码时：
   - 尽量让一个函数/对象**保持单一稳定形状**（后面隐藏类课程展开）
   - 避免在热函数里给变量"先 number 后 string"
2. **为什么说"不要过早优化"？** 普通函数可能根本不会被 TurboFan 优化（没成热点）。先把代码写清楚，用 Performance 面板测量，确认热点后再针对优化。
3. **阅读工具链源码**：Vue 模板编译（`compiler-core`）就是"模板字符串 → AST → render 函数"，和 V8 的流水线是同一种思维——遇到编译类框架源码不再陌生。

---

## 框架设计思想（如果我是 V8 架构师）

1. **为什么中间插字节码？** 直接源码→机器码启动快但内存爆；纯解释太慢。字节码层实现了"平台无关 + 启动可接受 + 为 JIT 提供基础"。核心是**在启动速度、内存占用、峰值性能三者间取舍**，不追求单项最优。
2. **为什么"解释 + 热点 JIT"（自适应优化）？** 大多数函数只执行几次，不值得优化。把编译成本花在真正热的少数代码上，性价比极高——和懒加载、Vue 异步组件是同一思路：**资源向热点倾斜**。
3. **为什么允许反优化？** 动态类型语言无法静态确定类型，只能靠运行时推测。**与其保守不优化，不如激进推测 + 错了回退**——整体期望收益更高。这是 JS 能接近静态语言速度的根本原因。

## 总结

**核心知识**：Parser（词法/语法分析 + 惰性解析）→ AST → Ignition 字节码 → TurboFan 热点优化编译 → 反优化回退。整条链路是"先跑起来，再逐步加速"的自适应编译策略。

**容易混淆**：

- 词法分析（切 token）≠ 语法分析（组装 AST）
- AST 不是 V8 独有，Babel/ESLint/Vue 编译器都用
- 字节码平台无关，机器码平台相关
- 反优化不是 bug，是"推测失败后的正常回退机制"，但频繁反优化会拖慢性能

**实际应用**：理解引擎怎么优化，就知道代码怎么写能"顺应优化"（类型稳定），也明白为什么要"先测量再优化"。
