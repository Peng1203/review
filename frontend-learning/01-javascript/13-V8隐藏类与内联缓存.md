# V8 隐藏类与内联缓存（Hidden Class & Inline Cache）

## 前置知识 & 知识网络

- **依赖**：V8 编译流水线（TurboFan 优化依赖隐藏类/IC 提供类型信息）
- **影响**：JIT 与去优化（下一章）、Vue 响应式性能、一切"对象访问快慢"的源码理解

---

## 一句话总结

JS 是动态语言，理论上每次 `obj.x` 都要做"属性名 → 位置"的哈希查找，很慢。V8 用**隐藏类（Map/Shape）**把对象形状固化成"属性名 + 偏移量"的描述表，再用**内联缓存（IC）**记住"上次访问的 map + 偏移"，让同一个调用点反复访问属性时，快得和 C 语言读结构体字段一样。

---

## 背景：动态语言的"性能原罪"

### 1. 静态语言凭什么快？

C++ 里 `struct Point { int x; int y; }` 编译后，`p.x` 就是"对象地址 + 固定偏移 0"，一条指令搞定，因为**类型在编译期已知，内存布局固定**。

### 2. JS 的困境

JS 对象是**动态的**：随时可以增删属性，同一个变量可以指向完全不同形状的对象：

```javascript
const p1 = { x: 1, y: 2 }
const p2 = { name: 'a', age: 3 }   // 完全不同形状

p1.z = 5        // 运行时再加属性
delete p1.y     // 还能删
```

如果没有优化，每次 `obj.x` 只能这样：

```text
a.x  ⟶  查"对象 → 属性字典"（本质是个哈希表）
         ⟶  对 "x" 做哈希 → 找到值
```

哈希查找每次几纳秒~几十纳秒，比固定偏移慢一个数量级以上。**一个页面几百万次属性访问，累积起来就是肉眼可见的差距。**

---

## 第一节：隐藏类（Hidden Class / Map）

### 思想：把"动态形状"偷换成"静态布局"

V8 给每个对象关联一个**隐藏类（V8 内部叫 Map，也叫 Shape）**，它记录：

```text
隐藏类 Map
├── 有哪些属性（属性名列表）
├── 每个属性在对象里的偏移量
└── 指向"下一个形状"的转换信息
```

对象本身不再存属性名，只按偏移存**属性值**：

```text
p = { x: 1, y: 2 }

隐藏类 C1                      对象 p（内存）
属性表:                         ┌──────────────┐
  x → offset 0      ──────►    │ 隐藏类指针 → C1│
  y → offset 1                 │ x = 1         │
                               │ y = 2         │
                               └──────────────┘
```

于是 `p.x` 变成两步：

```text
① 检查 p 的隐藏类是不是 C1（或包含 x 的描述）
② 直接按偏移 0 读内存
```

**形状相同 = 共享同一个隐藏类。** 只要对象是"同一个构造函数/同一种写法"创建的，它们共享一个 Map，编译器就能像对待同类对象一样优化。

### 形状转换链（Transition Tree）

对象不是一出生就固定形状的。加一个属性，隐藏类就要变一次：

```text
p = {}                空 Map0
p.x = 1               Map0 ──(加 x)──► Map1   p → Map1, x 在 offset 0
p.y = 2               Map1 ──(加 y)──► Map2   p → Map2, y 在 offset 1
```

如果又创建另一个对象走同样的加属性顺序：

```javascript
const q = {}
q.x = 1
q.y = 2
```

q 会沿着 Map0 → Map1 → Map2 的转换链走，最终停在同一个 Map2。所以 q 和 p 共享隐藏类。

**但如果顺序不一样，形状就不同：**

```javascript
const a = {}
a.x = 1
a.y = 2      // a → MapA：x@0, y@1

const b = {}
b.y = 2      // b → MapB1：y@0
b.x = 1      // b → MapB2：x@1, y@0
// a 和 b 属性一样，但顺序不同 → 不同隐藏类，无法共享
```

### 两个破坏形状的坏习惯

1. **动态加属性**：对象创建后再 `obj.newProp = v`，每次触发 map 转换；加多了 V8 干脆让对象进入**字典模式（慢模式）**，退化成纯哈希表。
2. **delete 属性**：删除会让形状不可复用，V8 常常直接把对象打入字典模式。

## 第二节：内联缓存（Inline Cache / IC）

### 隐藏类不够，还有"每次查 map"的开销

有了隐藏类，`obj.x` 仍需：① 读 obj 的隐藏类 ② 在隐藏类里找到 x 的偏移。隐藏类小还好，但大对象的属性表查找依然要花时间。

**IC 的直觉**：同一个调用点（比如同一个 `obj.x` 那一行），绝大多数时候遇到的**是同一个形状的对象**。那何必每次重新查？把第一次的结果"缓存"在调用点旁边。

### IC 的工作方式

```text
第一次执行 obj.x：
  调用点旁边开一个缓存槽：
  ┌────────────────────┐
  │ 槽：map = C1        │   ← 记录当时对象的隐藏类
  │     x 的偏移 = 0    │   ← 记录查到的偏移
  └────────────────────┘
  按偏移 0 读取

以后每次执行 obj.x：
  ① 检查 obj 的隐藏类 == 缓存里的 C1 吗？
     ├─ 是 → 直接用偏移 0 读（快路径，几乎零开销）
     └─ 否 → 重新查找，更新缓存槽
```

这条"隐藏类命中 → 直接按偏移读"的路径，就是优化代码里 TurboFan 生成的样子——**一个比较 + 一个内存读取**，和 C 语言的字段访问相差无几。

### 一个调用点遇到多种形状：单态 → 多态 → 超多态

IC 缓存槽有容量，遇到不同形状会升级：

```text
1 种形状    → monomorphic（单态）    最快，专用快路径
2~4 种形状  → polymorphic（多态）    多几条快路径分支，仍较快
>4 种形状   → megamorphic（超多态）  缓存失效，退回全量查找
```

**这就是为什么"类型/形状不稳定"是性能杀手**——类型漂移变慢，本质就是 IC 反复 miss + TurboFan 无法生成单一快路径。

## 整体流程图

```text
同一个调用点： obj.x

┌─────────────────────────────────────────────┐
│ 第一次执行                                    │
│   1. 读 obj 的隐藏类（Map）                   │
│   2. 在 Map 中查 "x" → 偏移 0                 │
│   3. 把 (Map, 偏移0) 写入调用点的 IC 缓存槽    │
└─────────────────────────────────────────────┘
              │
              ▼
┌─────────────────────────────────────────────┐
│ 之后每次执行（快路径）                         │
│   obj 的 Map == 缓存中的 Map ？               │
│     ├─ 是 → 直接按偏移读值  ← 一条指令        │
│     └─ 否 → 重新查找并更新缓存（慢路径）       │
└─────────────────────────────────────────────┘
```

## 结合实际开发

| 开发习惯 | 对引擎的影响 |
|---|---|
| 构造函数/类里**一次性初始化全部属性** | 实例共享隐藏类，可被优化 |
| 创建后再动态 `obj.xxx = v` | 触发 map 转换，多对象时破坏共享 |
| `delete obj.xxx` | 常致对象退化字典模式（慢） |
| 每次给对象赋值**顺序不一致** | 形状不同，无法共享隐藏类 |
| 同一个函数里传入**多种形状**的对象 | IC 变 megamorphic，慢路径 |

**Vue 相关（面试亮点）**：Vue 2 的 `Vue.set` / `this.$set` 之所以存在，是因为**直接给响应式对象新增属性，属性不是响应式的**（`Object.defineProperty` 只在初始化时拦截已有 key）——而 Vue 3 的 Proxy 没有这个限制。但从 V8 隐藏类角度，无论 Vue 2/3，**组件 data 尽量固定形状**、不要把数组下标当属性乱加，都对性能有利。

## 框架设计思想（如果我是 V8 架构师）

1. **为什么从 Self 语言借鉴隐藏类？** 1980 年代 Self 语言提出 Maps 思想，后来 JSCore、V8 都吸收。本质：**动态语言想快，就要在运行时"制造出类似静态类型的结构"**——隐藏类就是"运行期发现的对象布局缓存"。
2. **为什么叫"隐藏"类？** 因为 JS 程序员看不到它、不需要维护它，引擎自动维护——把负担从人转移到机器。
3. **为什么 IC 有容量上限、会退化？** 引擎无法预测未来遇到多少种形状。缓存槽有限是为了不浪费内存；退化成查找是"宁可慢也要正确"。**和 GC 一样：正确性是底线，性能是优化目标。**

## 总结

**核心知识**：动态属性访问慢 → 隐藏类把对象形状变成"偏移表"（同形状共享）→ IC 在调用点缓存 (map, 偏移) → 单态快、超多态退化。形状稳定 = 一切优化的前提。

**容易混淆**：

- 隐藏类不是对象的 `constructor`，也不是原型，是引擎内部的布局描述
- "相同属性" ≠ "相同隐藏类"，**属性顺序**也必须一致
- IC 缓存的是"调用点 + 形状"，不是缓存属性值

**实际应用**：构造函数一次性初始化全部字段、别乱 delete、保持对象形状统一 → 引擎自动受益。
